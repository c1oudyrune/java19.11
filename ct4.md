1. Статическое и динамическое связывание
Статическое (раннее) связывание решается на этапе компиляции: вызовы static, private, final методов, а также перегруженных методов — выбор версии по типу ссылки. Динамическое (позднее) связывание решается в рантайме по фактическому типу объекта через таблицу виртуальных методов — это вызовы переопределенных обычных методов экземпляра.
2. private/protected переменные в interface
До Java 8 полей в интерфейсах не было. С Java 9 разрешены private и private static методы — служебные, для устранения дублирования в default-методах. Переменных в интерфейсе никогда нет: только public static final константы (поля неявно таковы). protected использовать нельзя — поля только public static final, методы только public (до Java 9) плюс private.
3. ClassLoader
Компонент JVM, загружающий .class-файлы в память и превращающий их в объекты Class. Использует модель делегирования: запрос сначала уходит родителю (Bootstrap, Extension/Platform, Application), и лишь если родитель не нашел класс, загружает сам. Применение: загрузка классов по имени, динамическая подгрузка, кастомные ClassLoader (например, в серверах приложений и OSGi для изоляции версий).
4. Run-Time Data Areas
Области памяти, определенные в JVM-спецификации. Method Area — метаданные классов, статические поля, пул констант (Metaspace). Heap — все объекты. JVM Stack — фреймы методов с локальными переменными, на поток. PC Register — адрес текущей инструкции. Native Method Stack — для нативных методов. Плюс вспомогательные runtime-структуры, например String Pool.
5. Immutable object
Объект, состояние которого нельзя изменить после создания. Правила: поля final и private, нет сеттеров, для изменяемых полей возвращать копии, класс не должен расширяться (final/private конструктор), коллекции копировать. Примеры: String, Integer, record (Java 16+). Зачем: потокобезопасность, безопасное кэширование, надежные ключи в хеш-таблицах.
6. Особенности класса String
String неизменяем (immutable) и final. Хранит массив байтов/char и кэш хеша. Литералы интернируются в String Pool, поэтому == работает для них. Оператор + и concat() создают новые объекты (компилятор превращает конкатенацию в StringBuilder). Будучи immutable, класс потокобезопасен. Сравнивают строки через equals(), а не через ==.
7. Ковариантность типов
Возможность в переопределенном методе сузить возвращаемый тип по сравнению с методом родителя. Пример: class Animal { Animal make(){} } и class Cat extends Animal { @Override Cat make(){} } — Cat ковариантно расширяет возвращаемый тип. Работает только с reference-типами и только для возвращаемых значений.
8. Методы класса Object
toString(), equals(Object), hashCode(), getClass(), clone(), finalize() (deprecated), wait(), notify(), notifyAll().
9. Удачное и неудачное использование Optional
Удачно: Optional как возвращаемый тип, когда отсутствие значения допустимо и понятно, например Optional<Customer> findById(id), и цепочки map/filter/orElse. Неудачно: как поле класса, параметр метода или элемент коллекции; вызов get() без проверки; связка isPresent()+get() вместо ifPresent — антипаттерн; использование для обязательных значений — лучше вернуть значение напрямую.
10. main method как final
Да, public static final void main(String[] args) легально и работает. static обязателен, а final допустим — main-метод так и так не переопределяется.
11. Импорт одного package/class дважды
Можно: import java.util.*; и import java.util.ArrayList; вместе нормально компилируются. Последствие одно: если конкретный класс импортирован дважды разными одноименными путями — конфликт имен (ambiguous), компилятор выдаст ошибку. Двойной импорт сам по себе не ошибка, он просто избыточен.
12. Casting и ClassCastException
Casting — приведение типа. Явное приведение вниз по иерархии, например (Cat) animal, может не совпасть с фактическим типом объекта. Тогда возникает ClassCastException (unchecked), если объект не является экземпляром целевого класса и его предка. Чтобы избежать — проверка instanceof.
13. Почему фреймворки используют unchecked exceptions
Checked-исключения нужно объявлять в сигнатуре (throws) и обрабатывать, что засоряет код и заставляет клиента обрабатывать ошибки, которые он не может осмысленно разрешить. Unchecked (например, IllegalArgumentException, NullPointerException) позволяют передать ошибку вызывающему без обязательной обработки, упрощая API. Современные фреймворки предпочитают unchecked плюс центральный обработчик исключений (например, @ControllerAdvice).
14. static import
import static java.lang.Math.PI; позволяет использовать статические члены без имени класса: PI вместо Math.PI. Полезен для констант и утилит. Чрезмерное использование ухудшает читаемость.
15. Связь hashCode() и equals()
Золотое правило: если equals() считает два объекта равными, их hashCode() обязан быть одинаковым. Обратное не требуется. При нарушении объекты сломаются в HashSet/HashMap (потеряются поиск и удаление). Контракт equals: рефлексивность, симметричность, транзитивность, консистентность; равные объекты — равный хеш.
16. BufferedInputStream / BufferedOutputStream
Обертки над потоками, добавляющие буфер в памяти и сокращающие количество системных операций ввода-вывода (чтение/запись блоками). Используются при работе с файлами и сетью, когда выполняется много мелких операций чтения/записи — буферизация заметно повышает производительность. Необходимо вызывать flush() и закрывать поток.
17. Collection vs Collections
java.util.Collection — интерфейс корня иерархии коллекций (List, Set, Queue наследуют его). java.util.Collections — утилитный класс со статическими методами для работы с коллекциями: sort, reverse, unmodifiableList, synchronizedList, emptyList и другие.
18. Enumeration vs Iterator
Enumeration — старый интерфейс (hasMoreElements(), nextElement()), только для чтения, без удаления, появился в Java 1.0. Iterator — современный: hasNext(), next(), remove() (удаление), короче по именам, введен в Java 1.2. Iterator предпочтительнее.
19. fail-fast vs fail-safe
Fail-fast: итератор выбрасывает ConcurrentModificationException, если коллекция модифицируется во время обхода (проверка счетчика модификаций). Пример: ArrayList, HashMap. Fail-safe: итератор работает по копии (snapshot), поэтому не бросает исключение при модификации, но не видит новых изменений. Пример: ConcurrentHashMap, CopyOnWriteArrayList.
20. Модификатор transient
Помечает поле, которое не нужно сериализовывать. При стандартной сериализации (Serializable) значение такого поля пропускается, и при десериализации оно получает значение по умолчанию (0, null и т.п.). Пример: пароли, кэши, производные данные.
21. Влияние static и final на сериализацию
static-поля не сериализуются, так как принадлежат классу, а не объекту: при десериализации берутся текущие значения класса. final-поля сериализуются как обычные; после десериализации final-поле теоретически может быть изменено обходным путем. По факту final не исключает поле из сериализации.
22. Интерфейс Cloneable
Маркерный интерфейс без методов. Его реализация сообщает JVM, что объект можно клонировать через Object.clone(). Если класс не реализует Cloneable, вызов clone() бросит CloneNotSupportedException. clone() делает поверхностную копию (shallow); глубокую нужно реализовывать вручную. Интерфейс считается устаревшей практикой; предпочтительнее копирующие конструкторы или метод copy().
23. Интерфейс AutoCloseable
Интерфейс с одним методом close(). Объекты, его реализующие, можно использовать в try-with-resources: try (Resource r = ...) — ресурс автоматически закроется. Наследник Closeable добавляет throws IOException. Применяется для файлов, сокетов, подключений к БД — гарантированное освобождение ресурсов.
24. FunctionalInterface
Интерфейс ровно с одним абстрактным методом (может иметь default/static методы и наследованные). Аннотация @FunctionalInterface документирует это и дает ошибку компиляции при нарушении. Используется как тип для лямбд и ссылок на методы: Runnable, Comparator, Function, Supplier.
25. Atomic types
Классы пакета java.util.concurrent.atomic (например, AtomicInteger, AtomicReference): операции выполняются атомарно через CAS (compare-and-swap) без блокировок. Нужны для потокобезопасного инкремента и обновления общего состояния без синхронизации; эффективнее synchronized при конкуренции.
26. Happens-before и volatile
Happens-before — формальное отношение упорядочивания действий в JMM: если действие A happens-before B, то результат A виден в потоке B. Устанавливается через synchronized, volatile, start/join потоков. volatile гарантирует видимость записи другим потокам (запись happens-before чтение) и запрещает перемещение инструкций, но не дает атомарности составных операций, например x++.
27–28. Heap и Stack
Heap — общая для всех потоков область, где живут объекты и массивы; управляется GC, делится на поколения (young/old). Stack — per-thread, хранит фреймы методов, примитивы и ссылки на объекты; живость следует за вложенностью вызовов. Примитивы живут на стеке, объекты — в куче. Стек разгружается при завершении метода автоматически и быстро, heap — GC в фоне. Разделение нужно для эффективности: стек быстрый и поток-локальный, heap — общий для данных с неопределенным временем жизни.
29–30. Garbage Collector
JVM отслеживает достижимость объектов от корней (GC roots: статические поля, локальные переменные живых потоков, JNI-ссылки). Недостижимые объекты собираются. Heap делится на young (Eden + Survivor) и old. Reference counting — подсчет ссылок на объект, удаление при нуле; не используется в современных JVM из-за проблемы циклов. Tracing — обход графа объектов от корней с алгоритмами mark-and-sweep/sweep-compact (Serial, G1, ZGC).
31. Autoboxing
Автоматическое преобразование примитива в обертку и обратно: Integer x = 5; и int y = x;. Компилятор генерирует valueOf() и intValue(). Нюансы: Integer кэширует значения от -128 до 127 (== сравнивает по значению в этом диапазоне); autoboxing в циклах создает лишние объекты.
32. Сериализация в Java
Превращение объекта в поток байтов через интерфейс Serializable и ObjectOutputStream.writeObject() / ObjectInputStream.readObject(). Хранится схема сериализации, serialVersionUID для контроля совместимости. Применяется: сохранение состояния, передача по сети (RMI), кэширование, очереди сообщений. Альтернативы: JSON/XML (Jackson, Gson), не требующие serialVersionUID.
33. WeakReference vs SoftReference
SoftReference удерживает объект, пока памяти достаточно; GC удалит объект только при нехватке памяти (до OutOfMemoryError). Используется для кэшей. WeakReference позволяет собрать объект на ближайшем GC, если он слабо достижим. Используется для вспомогательных структур (WeakHashMap, метаданные). Для обоих обязательно проверять ref.get() на null.
34. Дедлок (deadlock)
Ситуация, когда два или более потоков вечно ждут друг друга: каждый держит ресурс, нужный другому, и никто не освобождает. Причины — пересечение блокировок в разном порядке. Последствия: зависание системы. Решение: единый порядок захвата замков, tryLock с таймаутом, lock-free структуры. Дедлоки не нужны — это дефект; вопрос в том, как они возникают и как их избегать.
36. Зачем на практике immutable объекты
Потокобезопасность без синхронизации; безопасное переиспользование и кэширование; надежные ключи в HashMap/HashSet, так как состояние не изменится после вставки; упрощенное рассуждение о коде и безопасная передача по ссылкам; удобные value-семантика и equals/hashCode. Примеры: String, LocalDate, DTO-записи (record).
37. Maven, Ant, Gradle
Инструменты сборки Java-проектов. Ant: XML-скрипты, гибкие задачи, но без автоматического управления зависимостями и жизненным циклом. Maven: декларативный XML (pom.xml), фиксированный жизненный цикл, автоматическое управление зависимостями из центрального репозитория. Gradle: скрипты на Groovy/Kotlin DSL, инкрементальная быстрая сборка, гибкость Ant плюс управление зависимостями как в Maven.
38. Spring core, IoC, DI
Spring Core — ядро фреймворка: контейнер бинов с управлением через Inversion of Control и Dependency Injection. IoC означает, что создание и жизненный цикл объектов переданы контейнеру, а не коду. DI — зависимости внедряются в класс (через конструктор, сеттер или поле), а не создаются внутри. Это развязывает код, упрощает тестирование и замену реализаций.
39. Как «под капотом» работает @Transactional
Spring оборачивает метод в прокси (AOP). При вызове открывается или присоединяется транзакция к текущему соединению (через ThreadLocal ConnectionHolder), выполняется бизнес-код, при успехе — commit, при RuntimeException — rollback (настраивается и для checked-исключений). Работает только через прокси, поэтому самовызов this.method() транзакцию не создает. Управляет распространением (propagation), уровнем изоляции и режимом readOnly.

Базы данных, библиотеки и стандарты (40–48)
40. Реляционные vs нереляционные БД
Реляционные (SQL): данные в таблицах со строгой схемой и связями, поддержка ACID-транзакций, язык SQL, нормализация. Подходят для структурированных данных и требовательной к целостности нагрузки (банки, ERP). Примеры: PostgreSQL, MySQL, Oracle. Нереляционные (NoSQL): гибкие или отсутствующие схемы, горизонтальное масштабирование, разные модели хранения (документы, ключ-значение, графы, колонки). Жертвуют строгой целостностью ради производительности и масштабируемости. Примеры: MongoDB, Redis, Cassandra, Neo4j.
41. Связи one-to-one, one-to-many, many-to-many
One-to-one: в таблице B добавляется внешний ключ на A (часто с ограничением UNIQUE) или общий первичный ключ. One-to-many: в таблице «многие» (children) хранится внешний ключ на «один» (parent). Many-to-many: нужна связующая (junction) таблица с двумя внешними ключами, уникальность каждой пары. Пример: students и courses через таблицу student_course(student_id, course_id).
42. Нормализация БД
Процесс устранения избыточности и аномалий путем разбиения таблиц по нормальным формам. 1НФ: атомарные значения, нет повторяющихся групп. 2НФ: 1НФ плюс отсутствие частичной зависимости от составного ключа. 3НФ: 2НФ плюс отсутствие транзитивных зависимостей. Пример из реального проекта: вместо таблицы «Заказ» с повторяющимися данными клиента — отдельные таблицы Customer, Order, OrderItem, а адрес клиента хранится один раз и не дублируется в каждом заказе.
43. Виды индексов в БД
B-tree index — стандартный, для равенства, диапазонов и ORDER BY. Hash index — быстрое точное равенство, не для диапазонов. Bitmap index — для низкокардинальных колонок (пол, статус). Composite (многоколоночный) — по нескольким колонкам, важен порядок. Full-text index — полнотекстовый поиск. Partial (условный) и Covering (покрывающий) индексы. GIN/GiST в PostgreSQL — для JSON, массивов, геометрии.
44. Hibernate, разница JPA и Hibernate
Hibernate — мощный ORM-фреймворк для Java: отображает классы на таблицы БД, управляет состоянием сущностей, кэшем и генерацией SQL. JPA (Jakarta Persistence API) — спецификация/стандарт, набор интерфейсов и аннотаций (@Entity, EntityManager, @PersistenceContext), а не реализация. Hibernate — реализация JPA, плюс собственные расширения вроде HQL и своих типов. Код на чистой JPA переносим между провайдерами (Hibernate, EclipseLink, OpenJPA).
45. Каскадность, использование в Hibernate
Каскад — автоматическое распространение операции (persist, merge, remove и другие) с родителя на связанные сущности. Задается через @OneToMany(cascade = CascadeType.ALL). Пример: удалив Order, автоматически удалятся связанные OrderItem. Осторожность: агрессивные каскады могут случайно удалить данные; стоит продумывать orphan-удаление. Каскад Hibernate работает на уровне сущностей, тогда как ON DELETE CASCADE — каскад на уровне БД.
46. Может ли entity-класс быть абстрактным
Да. Абстрактный @Entity-класс служит базой для наследников в стратегиях наследования (SINGLE_TABLE, JOINED, TABLE_PER_CLASS). Сам по себе он не мапится на таблицу; может содержать общие поля, @Id, @EmbeddedId и маппинг общих свойств. Это удобный способ выделить общую супертип-структуру.
47. EntityManager и его функции
EntityManager — центральный интерфейс JPA для работы с сущностями в контексте персистентности. Отвечает за: persist (закрепить новый объект), merge (обновить), remove (удалить), find (найти по id), создание запросов createQuery (JPQL), управление транзакцией через getTransaction(), а также flush и clear; управляет жизненным циклом сущностей (transient, managed, detached, removed) и кэшем первого уровня.
48. Класс Assert
Класс org.junit.jupiter.api.Assertions (JUnit 5; в JUnit 4 — org.junit.Assert). Используется в юнит-тестах для проверки ожидаемых результатов. Методы: assertEquals (сравнение значений), assertTrue/assertFalse, assertNull/assertNotNull, assertSame/assertNotSame (по ссылке), assertThrows (проверка исключения), assertAll. При провале тест падает с сообщением. Пример кода: assertEquals(4, calculator.add(2, 2)); assertThrows(ArithmeticException.class, () -> calculator.divide(1, 0));
